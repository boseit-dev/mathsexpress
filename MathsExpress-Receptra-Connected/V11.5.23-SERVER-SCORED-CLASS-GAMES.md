# MathsExpress v11.5.23 — Correctness / security fixes

**Date:** 11 October 2026  
**Status:** Updated source archive; NOT deployed to production. No production data or functions were changed by this release.  
**Starting point:** v11.5.22 (45 passing tests).

## What was actually changed

1. **Class-game grading is now designed to run on the server.** The client fetches a question through `mathsexpress_class_game_next_question` and sends the chosen option, not an untrusted `correct: true/false` flag. The marking key is stored in a private table and never returned with the question.
2. **Server-side duplicate protection and concurrency guard.** The new migration creates per-student question rows, a unique scored-submission ledger, locks the player record during scoring and enforces a three-second answer cooldown. Old two-argument client-score calls are explicitly revoked. The new 3-argument function calls the existing scoring engine only after checking the submitted answer. No fallback is provided to the unsafe old endpoint.
3. **Reload-safe questions.** Students rejoining from another tab or device receive their unfinished server-issued question rather than getting a second answer opportunity for the same question. The server prevents scoring the same issued question twice.
4. **Daily attempt tracking is a real, separate RPC**, backed by its own private table. It does **not** issue XP or spend reward event keys. A given event key is logged once per user.
5. **Signup without returned tokens now works with Supabase's actual hosted signup contract.** If confirmation is required, the account stays logged out and the UI asks the user to verify the email. Otherwise, the browser uses ordinary Supabase password sign-in, since the hosted signup function intentionally does not return access/refresh tokens.
6. **Resend verification actually calls Supabase Auth** rather than returning a fake success result.
7. **Class-game cooldown and blocked submissions:** both correct and incorrect answers respect the server cooldown; a `cooldown` response lets the same question be retried instead of marking it submitted.
8. **Year 0 difficulty:** the new server question call handles year level `0` instead of accidentally treating it as Year 9.
9. Release URL versions and the service worker's cache name updated to v11.5.23.

## Required steps before this can work on the live website

**This release is NOT a drop-in production deploy.** The client now REQUIRES new server RPCs. An app-only deploy will break class games. Apply database changes in the correct order and test safely before publishing:

1. Confirm the live worker version and back up the database. If anyone deployed newer work, merge those changes first.
2. The older `supabase/migrations/20261011_01_discussion_and_parent_links.sql` is still pending according to the supplied handoff; verify whether it was applied before deciding whether to run it.
3. Review the new `20261011_02_class_game_idempotency_and_daily_attempts.sql` against the live database schema. It was written using **read-only introspection of the actual MathsExpress project**, but it **has not been applied or tested in a staging database**.
4. Test the SQL in a separate staging environment with at least one student and one teacher account, including RLS, two-browser concurrency, missing/invalid question keys, valid and incorrect answers, resuming a question, and direct old-endpoint rejection.
5. Apply the migration using the approved migration workflow and release the matching v11.5.23 client in coordination. Never publish one without the other.
6. In Supabase Auth, separately decide/enable email confirmation. This ZIP does **not** change that account-level setting; it changes the client so it handles either setting truthfully.
7. Test email signup, confirmation, login and class-code joining in real browser sessions. With confirmation on, the student joins their class **after login** using their code.
