# MathsExpress v11.5.35 — multiple-choice freeze, and asset caching

Two fixes for "some buttons freeze the website" and "some pages take 5 seconds
to load". Both were reproduced before being changed.

## 1 · Multiple-choice questions could hang the tab

`mcQuestion` in `deploy-core-1.js` pads a question out to four options. Every
candidate was built from `Number(answerText)`:

```js
const candidate = String(Number(answerText) + answers.length + filler);
filler += 1;
if (seenLabels.has(candidate)) continue;
```

`Number('evening')` is `NaN`, and `NaN + anything` is `NaN`, so for any answer
that is not a number the candidate was the string `'NaN'` on every pass.
`filler` kept incrementing but the value never changed, so once `'NaN'` had been
taken the `continue` spun forever and the tab froze. No error, no console
output — the page simply stopped.

Of the 125 `mcQuestion` call sites, many pass words, fractions or symbols:
`'eat breakfast'`, `'evening'`, `'1/3'`, `'>'`, `'They are the same length'`.
Any of those with fewer than three usable distractors froze the browser.

**Fix.** A numeric answer still gets near-miss neighbours and is padded to four,
with identical output to before. A word, fraction or symbol has no arithmetic
neighbour, so the question now keeps whatever distractors it supplied rather
than inventing a nonsense fourth option that gives the real answer away. A
single-option question is still padded, because two is the minimum that can be
asked. Both loops are bounded, so no later edit can hang the page here again.

Covered by `tests/mc-option-padding.test.cjs`, which runs the shipped padding
block under a timeout for words, fractions, symbols, sentences, and a number too
large to increment.

## 2 · Every asset was revalidated on every page load

`public/_headers` set no `Cache-Control` for any script or stylesheet, so they
were served with the default:

```
Cache-Control: public, max-age=0, must-revalidate
```

That is a network round trip for all 13 bundles on every single page load —
about 2.2 MB of JavaScript and CSS — before the page can do anything. On a
school network that is most of the five seconds.

**Fix.** The bundles are now cached for a day with a week of background
revalidation. This is safe because every one is requested with a `?v=<version>`
string that changes on release, so a new version is a different URL and is
fetched immediately; the day-long window only covers the service worker, which
pre-fetches the same files without the query string.

Three things are deliberately excluded:

- `service-worker.js` is `no-cache`. It is the mechanism that ships every other
  update, so caching it means a bad release can never be replaced.
- `app.html` and `index.html` are `no-cache`. They carry the `?v=` strings.
- The rules name each file rather than using `/*.js`, which would also have
  matched `service-worker.js` and left its caching dependent on rule precedence.

Covered by `tests/cache-headers.test.cjs`, and verified against `wrangler dev`
rather than assumed.

## Also

Five tests pinned the literal string `v11.5.34`, so they failed on the next
release instead of catching the mistake they were written for. The two that
guard the release now read the current version out of `app.html` and check the
service-worker cache name tracks it, which is the invariant that actually
matters: if those drift apart, a release ships to browsers that keep serving the
old copy.

## Verified

104 tests pass. Served headers confirmed with `wrangler dev`. The freeze was
reproduced against the real source before the fix and does not reproduce after.

## Not included

Page speed has a second half this does not touch: `deploy-app.js` is a single
1 MB file with no splitting or lazy loading, and some screens wait on several
server calls with 3–6 second timeouts. Both need profiling while signed in.
